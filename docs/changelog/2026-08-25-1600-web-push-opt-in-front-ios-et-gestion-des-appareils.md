# 2026-08-25 — Web Push : opt-in front, entonnoir iOS et gestion des appareils (#498)

Partie visible du Web Push : demander la permission au bon moment, gérer le cas iOS, et laisser l'utilisateur reprendre la main ensuite. Clôt le lot Web Push de l'épic #481.

- **Service worker** (`inertia/sw.ts`) : gestionnaire `push` qui appelle **toujours** `showNotification` — même payload vide/invalide, Safari et Chrome désabonnent un endpoint muet — avec un `tag` par type (les alertes récurrentes coalescent, pas douze « en retard ») ; gestionnaire `notificationclick` : fenêtre existante → `focus()` + `postMessage` → `router.visit(url)` dans le layout (navigation Inertia, pas de rechargement complet), sinon `openWindow(url)`. Le parsing du payload est extrait en **fonction pure** `inertia/lib/push_payload.ts` (ne lève jamais ; une `actionUrl` non relative retombe sur `/notifications`).
- **`use_push_notifications.ts`** : `isSupported`/`permission`/`isSubscribed`/`subscribe()`/`unsubscribe()` + `urlBase64ToUint8Array`. **`subscribe()` uniquement depuis un geste utilisateur** — l'initialisation ne fait que lire l'état, jamais de prompt à froid. Sync serveur via `router.post`/`router.delete` sur `/push/subscriptions`.
- **`PushOptInCard.vue`** (montée dans `default.vue`) : opt-in contextuel à partir de la **2e session** (compteur localStorage + marqueur sessionStorage), dismissible, masquée si permission refusée/déjà abonné/push non configuré. Sur iOS hors PWA : montre l'entonnoir au lieu du bouton.
- **`IosInstallHint.vue`** : Web Push iOS exige la PWA installée (16.4+) et Safari n'émet jamais `beforeinstallprompt` — instructions illustrées « Partager → Sur l'écran d'accueil ». `isIos()`/`isStandalone()` exposés par `use_pwa_install.ts` (iPadOS « MacIntel » tactile inclus).
- **Écran de gestion** : nouvel onglet Réglages → Notifications (`/settings/notifications`, visible pour tous les rôles) — activer/désactiver **cet appareil**, liste des appareils abonnés (`user_agent`, ajouté le / dernière notification) et retrait par appareil. Backend : action `SettingsController.notifications` + route `settings.notifications`.
- **i18n.** 8 clés `common.push.*` + section `settings.notifications.*` dans les deux locales (vouvoiement FR). #459 étant réglée, les clés résolvent.
- **Doc.** `docs/frontend/pwa.md` (section Web Push), `docs/domain/notifications.md`, `docs/frontend/ui-map.md`.
- **Tests (21 nouveaux, verts).** `push_payload.spec.ts` : payload complet, vide → notification générique, JSON invalide → texte en corps sans throw, tag par type, URL non relative neutralisée. `use_push_notifications.spec.ts` (SW/PushManager stubbés) : **aucun `pushManager.subscribe` hors geste utilisateur**, souscription + POST serveur, refus de permission, absence de clé VAPID, désabonnement navigateur + DELETE serveur, conversion base64url. `ios_install_hint.spec.ts` : affiché Safari iOS non installé, masqué standalone et hors iOS, clés traduites. Fonctionnel : `GET /settings/notifications` rend la page avec les appareils.
