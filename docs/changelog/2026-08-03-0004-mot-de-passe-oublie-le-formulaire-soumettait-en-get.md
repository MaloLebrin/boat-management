# 2026-08-03 — « Mot de passe oublié » : le formulaire soumettait en GET (#449)

Aucun email de réinitialisation ne partait. `inertia/pages/auth/forgot_password.vue` utilisait `<Form route="password.forgot">`, or ce nom désigne la route **GET** `/forgot-password` (`start/routes/auth.ts:14`) — et `<Form>` reprend `methods[0]` de la route nommée. La soumission partait donc en GET : l'email atterrissait en query string (`/forgot-password?email=…`, donc dans l'historique du navigateur, le `Referer` et les logs d'accès), la route POST qui partage le même chemin n'était jamais atteinte, et la page se re-rendait vide sans le moindre message.

- **Le formulaire poste.** `<Form route="password_reset.store">` — le nom auto-généré de `router.post('forgot-password', …)`, typé par le registre Tuyau comme `session.store` sur le login et `new_account.store` sur l'inscription. Aucun changement côté serveur : le contrôleur et la route POST étaient corrects, ils n'étaient simplement jamais appelés.
- **Garde statique générique** (`tests/inertia/form_route_methods.spec.ts`). Les deux routes partagent le chemin `/forgot-password` : lire l'URL ne distingue rien, c'est le **verbe derrière le nom** qui compte. Le test relit tous les `.vue` de `inertia/`, extrait chaque `route="…"` de `<Form>` et le résout dans `.adonisjs/client/registry` — exactement la source que le composant interroge au runtime. Il échoue si un `<Form>` vise une route en lecture seule (avec le fichier, le nom et le verbe fautifs) ou un nom absent du registre. Vérifié en réintroduisant `route="password.forgot"` : 2 tests tombent. Un méta-test vérifie que le piège existe toujours (une route GET sur le même chemin), pour que la garde ne devienne pas vacante.
- **Contrat des deux routes homonymes** (`tests/functional/auth/forgot_password.spec.ts`, 5 tests) : le POST émet un token et redirige vers `/forgot-password` ; le GET avec l'email en query string — la requête exacte que produisait le bug — n'émet **rien** ; une adresse inconnue est indiscernable d'une adresse connue (statut et redirection identiques, pas d'énumération de comptes) ; un email malformé n'émet pas de token ; une seconde demande remplace le token précédent au lieu d'en empiler un.
- **Reproduction navigateur** (`tests/browser/auth.spec.ts`) : le formulaire réel est rempli dans le DOM, la page doit exposer un `form[action="/forgot-password"][method="post"]`, le panneau de confirmation doit remplacer le formulaire et un token doit exister en base — avec `route="password.forgot"`, le `<form>` sort en `method="get"` et le test échoue au premier assert. C'est le niveau qui rejoue exactement la campagne de test du 03/08.
- **Au passage**, deux liens de la même page : le retour vers la connexion passe de `<a href>` à `<Link>` (le `<a>` forçait un rechargement complet, contraire à la convention Inertia du projet), et « ↻ Renvoyer » — affiché après l'envoi — pointait vers `/login` au lieu de ramener au formulaire ; il pointe désormais vers `/forgot-password`.
