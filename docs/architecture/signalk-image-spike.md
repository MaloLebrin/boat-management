# Spike — base de l'image Raspberry Pi « Signal K plug and play » (#1032, section C)

> Issue [#1032](https://github.com/MaloLebrin/boat-management/issues/1032), épopée [#986](https://github.com/MaloLebrin/boat-management/issues/986). Spike : **aucune image n'est construite ici**, aucun dépôt n'est créé. Ce document tranche la base, liste les risques et ce qui reste à prouver sur matériel.
>
> Rédigé le 2026-10-26 à partir des sources primaires listées au §10 (documentation et dépôts lus ce jour). **Aucun test sur Raspberry Pi réel** n'a été fait. Chaque fait important porte une étiquette :
>
> - **[V]** vérifié dans la source citée ;
> - **[D]** déduit (raisonnement, connaissance générale non relue ce jour) — à confirmer ;
> - **[M]** exige un test sur matériel réel (Pi 4 et Pi 5, PICAN-M, Actisense NGT-1…).

## 1. Décision

**Construire l'image sur Raspberry Pi OS Lite 64 bits (Debian 13 « Trixie »), avec Signal K (npm, service systemd) et le plugin `signalk-fleetai` en mode appairage préinstallés, assemblés par `pi-gen` en CI.** Pas de surcouche d'OpenPlotter, ni de HaLOS.

Les trois raisons qui tranchent, toutes **[V]** :

1. **OpenPlotter contredit deux critères durs.** Sa documentation impose de répondre **NON** aux réglages de l'Imager, d'utiliser l'utilisateur `pi`, et livre `pi` / `raspberry` ([installation](https://openplotter.readthedocs.io/latest/getting_started/installing.html), [téléchargement](https://openplotter.readthedocs.io/latest/getting_started/downloading.html)). Le Wi-Fi préréglé et le « jamais de mot de passe commun » sont donc impossibles sans forker l'image — ce qui revient à reconstruire OpenPlotter.
2. **Le Wi-Fi préréglé dans l'Imager dépend du format d'image, pas de la distribution.** Raspberry Pi OS Trixie utilise `init_format: cloudinit-rpi` ([doc Imager](https://github.com/raspberrypi/rpi-imager/blob/main/doc/os_customisation_formats.md), [liste d'OS](https://downloads.raspberrypi.com/os_list_imagingutility_v4.json)). Partir de cette base, c'est hériter du mécanisme que l'Imager sait piloter. Voir le piège du §4.
3. **Le script existant (#1021) suppose déjà ce modèle** : Signal K installé par npm, plugin dans `~/.signalk`. L'image n'est « que » ce que le client ferait à la main, figé et durci.

**Le point qui peut tout changer** (§4) : pour qu'un client qui choisit « Utiliser une image personnalisée » voie les réglages Wi-Fi de l'Imager 2.x, l'image doit être **déclarée dans un manifeste d'OS** (`init_format: cloudinit-rpi`). Sinon l'Imager 2.x ne propose **aucune** personnalisation. Le parcours cible de l'issue (étape 2) n'est donc **pas acquis** ; le point d'accès de repli (§5) n'est plus une option mais le filet de sécurité principal.

**Pourquoi pas une surcouche d'OpenPlotter, même « juste en ajoutant FleetAi ».** Au-delà des deux critères durs, l'image est construite par un fork de `pi-gen` (branche `openplotter64`) et le projet affirme que changer le nom d'utilisateur casse OpenPlotter [V]. On hériterait d'un contrat (utilisateur `pi`, interface graphique, apps wxPython) dont FleetAi n'a aucun usage, avec un entretien amont ralenti [V : dates de dernier push]. En revanche **OpenPlotter reste le bon renvoi pour un client qui l'utilise déjà** : le script #1021 fonctionne dessus, et la page publique le cite déjà.

**Pourquoi pas HaLOS.** C'est la référence la plus proche (images `pi-gen`, publiées en releases GitHub, AP `Halos-XXXX` qui coexiste avec le client Wi-Fi), mais il impose Internet au premier démarrage pour tirer ses conteneurs, des mots de passe communs documentés et une pile (Traefik, Authelia, Cockpit) que le coffret n'a pas à porter [V]. À lire pour ses scripts d'AP, pas à forker.

## 4. Wi-Fi au premier démarrage : ce que l'Imager honore réellement

Faits **[V]** ([doc Imager](https://github.com/raspberrypi/rpi-imager/blob/main/doc/os_customisation_formats.md), [liste d'OS](https://downloads.raspberrypi.com/os_list_imagingutility_v4.json), [article cloud-init](https://www.raspberrypi.com/news/cloud-init-on-raspberry-pi-os/)) :

- L'Imager lit `init_format` dans le manifeste de l'OS : `none`, `systemd` (`firstrun.sh`), `cloudinit`, `cloudinit-rpi`, `rpi-preseed`.
- Pi OS Bookworm → `systemd` ; Pi OS Trixie actuel → `cloudinit-rpi` (la toute première Trixie du 2025-10-01 était encore en `systemd`).
- **Imager 1.x ne sait pas personnaliser Trixie** : il suppose `systemd`, « applique » sans effet. Imager 2.x sait tout faire.
- **Image locale (« Utiliser une image personnalisée »)** : l'Imager 2.x suppose `init_format: none`, donc **ne propose aucune personnalisation**. Il faut un manifeste local (`create_local_json.py`) ou un dépôt personnalisé (`--repo <URL>` au lancement de l'Imager).
- Des images tierces hébergées en releases GitHub **figurent dans la liste officielle** avec leur `init_format` : MainsailOS et MoodleBox (`cloudinit-rpi`), OctoPi, DuetPi, Homebridge (`systemd`) ; ni OpenPlotter ni HaLOS n'y sont.
- Le manifeste porte `extract_sha256` (« critique pour la sécurité ») que l'Imager vérifie ([schéma](https://github.com/raspberrypi/rpi-imager/blob/main/doc/schema-notes.md)).
- Avec cloud-init, le Wi-Fi passe par Netplan avec le rendu NetworkManager ; `network-config` et `user-data` sont lus sur la partition boot [V].
- `pi-gen` installe cloud-init + Netplan par défaut (`ENABLE_CLOUD_INIT=1`) [V].

**Conséquences pour FleetAi :**

| Voie de distribution                              | Wi-Fi Imager honoré ?         | Coût pour le client                                                                                                                                                      |
| ------------------------------------------------- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Liste officielle de l'Imager (comme MainsailOS)   | Oui, `cloudinit-rpi`          | Aucun : choisir « FleetAi » dans la liste. **Démarche d'inscription non documentée dans les sources lues** : à demander à Raspberry Pi [D].                              |
| Dépôt personnalisé : manifeste FleetAi + `--repo` | Oui                           | Lancer l'Imager avec un argument : trop technique pour le public visé, **à proscrire pour le niveau 1** sauf s'il existe un moyen de l'ouvrir par lien [D, non vérifié]. |
| « Utiliser une image personnalisée »              | **Non** (Imager 2.x : `none`) | Aucune saisie possible dans l'Imager ; reste Ethernet ou point d'accès.                                                                                                  |
| Imager 1.x sur image Trixie                       | **Non** (ignoré en silence)   | À signaler dans la page publique : exiger Imager ≥ 2.x.                                                                                                                  |

**À valider [M]** : (1) l'image construite, une fois déclarée `cloudinit-rpi`, rejoint bien un Wi-Fi saisi dans l'Imager 2.x, sur Pi 4 et Pi 5, 2,4 et 5 GHz ; (2) le pays Wi-Fi (régulation) est appliqué ; (3) le comportement quand l'utilisateur coche la personnalisation mais saisit un SSID erroné (doit retomber sur le point d'accès, §5).

**Plan B documenté dans l'image** : lire aussi un fichier optionnel sur la partition FAT (`fleetai-wifi.txt`, SSID + mot de passe + pays) pour un client qui ne passe pas par le manifeste ; coût faible, utile pour le support [D].

`rpi-preseed` (nouveau format TOML de Raspberry Pi) est à **ignorer** : son dépôt se déclare « prototype, pas encore durci pour la production » [V](<[README](https://github.com/raspberrypi/rpi-preseed)>).

## 5. Point d'accès de repli et visibilité de l'état

**Faisable [V/M].** Les deux concurrents l'ont : HaLOS démarre `Halos-XXXX`, puis le conserve comme AP **en parallèle** du client Wi-Fi en déplaçant le hotspot sur le canal du réseau rejoint [V]([premier démarrage](https://docs.halos.fi/getting-started/first-boot/)) ; OpenPlotter propose « Hotspot+Client » sur le Wi-Fi interne via NetworkManager [V]([doc réseau](https://openplotter.readthedocs.io/latest/network/network_app.html)). **Pi 4 et Pi 5 en AP+client simultanés avec notre noyau et NetworkManager : [M].**

Briques disponibles **[V]** (activité et licence lues sur l'API GitHub, comportement non testé) :

| Brique                                                             | Licence    | Dernier push | Remarque                                                                             |
| ------------------------------------------------------------------ | ---------- | ------------ | ------------------------------------------------------------------------------------ |
| [balena `wifi-connect`](https://github.com/balena-os/wifi-connect) | Apache-2.0 | 2026-10-22   | Portail captif sur NetworkManager ; compatibilité Trixie/Pi 5 et binaire arm64 : [M] |
| [Comitup](https://github.com/davesteele/comitup)                   | GPL-2.0    | 2026-08-18   | Alternative éprouvée ; GPL                                                           |
| [RaspAP](https://github.com/RaspAP/raspap-webgui)                  | GPL-3.0    | 2026-10-24   | Trop large (routeur complet)                                                         |

**Recommandation** : petit service FleetAi maison (≈ 150 lignes, NetworkManager via `nmcli`/D-Bus, page statique + formulaire) **ou** `wifi-connect`, à départager sur matériel ; dans les deux cas, déclenché seulement si aucune connexion (Ethernet ou Wi-Fi) n'est active après N secondes et qu'il n'y a pas d'Internet.

**Questions de conception à trancher avant la construction :**

- **Mot de passe de l'AP.** Ouvert : le mot de passe du Wi-Fi du bord circule en clair sur l'air, dans une marina. Mot de passe fixe commun : contredit le critère « pas de secret commun » (c'est le défaut d'OpenPlotter et de HaLOS [V]). Mot de passe **aléatoire par boîtier**, affiché sur la console, la page locale (inutile hors AP) et, au niveau 2, sur l'étiquette du coffret : plus sûr, mais **invisible pour un client niveau 1 sans écran**. Recommandation : WPA2 avec secret aléatoire par boîtier, et pour le niveau 1 documenter qu'Ethernet ou le Wi-Fi préréglé restent les chemins normaux ; l'AP sert au dépannage. À arbitrer avec Malo.
- **Visibilité sans réseau.** Pas de code d'appairage sans Internet : l'état doit être lisible. Moyens : message sur la console HDMI, page `fleetai.local`/IP, nom du SSID de l'AP (`FleetAi-xxxx`), et **LED d'activité de la carte** pilotée par motif (clignotement distinct « pas de réseau », « réseau sans Internet », « en attente d'appairage », « connecté ») via `/sys/class/leds` [D, accès à confirmer sur Pi 5 : M].

## 6. Compte, SSH, sécurité Signal K

- **SSH désactivé par défaut** : `ENABLE_SSH=0` est la valeur par défaut de `pi-gen` [V]. L'Imager, s'il personnalise, peut l'activer ; c'est un choix du client.
- **Pas d'utilisateur à mot de passe connu.** `pi-gen` : si `FIRST_USER_NAME=pi` sans `FIRST_USER_PASS`, l'assistant de premier démarrage demande le mot de passe [V]. Pour une image sans écran, ne **pas** laisser cet assistant ouvert : verrouiller le compte, laisser cloud-init créer l'utilisateur de l'Imager quand il y en a un [V pour le mécanisme, M pour le résultat].
- **Sécurité Signal K : le piège du « premier arrivé ».** Le script d'installation de Signal K active la sécurité et invite à créer l'admin au premier « Login » [V](<[doc](https://github.com/SignalK/signalk-server/blob/master/docs/installation/raspberry_pi_installation.md)>). Sur un serveur frais, l'endpoint `POST /skServer/enableSecurity` accepte un `adminUser {userId, password}` **tant qu'aucun utilisateur n'existe** puis répond 403 [V](<[`serverroutes.ts`](https://github.com/SignalK/signalk-server/blob/master/src/serverroutes.ts)>). Donc, sans précaution, **le premier visiteur du réseau du bord devient administrateur**. L'image doit créer l'admin elle-même **avant** que Signal K n'écoute hors `localhost` : un service de premier démarrage lance Signal K en boucle locale, appelle `enableSecurity` avec un mot de passe aléatoire, enregistre le secret en `0600`, puis ouvre l'écoute LAN [D, mécanisme prouvé dans le code ; séquence à tester : M].
- **Où l'utilisateur lit ce mot de passe ?** Pas sur la page locale (visible de tout le réseau). Proposition : console HDMI et fichier sur la partition FAT (`fleetai-credentials.txt`, lisible en rebranchant la carte, donc réservé à qui a l'accès physique, qui a de toute façon la main sur la carte). L'appairage ne nécessite **pas** ce mot de passe (le plugin utilise le jeton d'ingestion) ; il sert à ouvrir l'admin Signal K. Alternative à étudier : ne jamais le divulguer et passer par un jeton d'accès (`signalk-generate-token` [V]) livré à FleetAi. À arbitrer.
- Les jetons `fai_ing_…` vivent dans `plugin-config-data/signalk-fleetai.json` en `0600` (comme le script #1021 [V]).

## 7. Pilotes, bus CAN et détection du matériel

Ce que `pi-gen` sur Pi OS donne sans effort : le noyau Raspberry Pi avec l'overlay `mcp2515-can0` [V], SocketCAN, les pilotes USB-série. Ce que **personne ne fournit** et qu'il faut écrire :

| Matériel                            | Mécanisme                                                                                                                                                                                       | Reste à faire                                                                                                                                                                                                                              |
| ----------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **PICAN-M** (MCP2515 sur SPI)       | `dtparam=spi=on` + `dtoverlay=mcp2515-can0,oscillator=…,interrupt=…` dans `config.txt`, puis `can0` à 250 kbit/s [V pour l'overlay ; D pour les paramètres PICAN-M, à relire chez le fabricant] | Savoir **si la carte se détecte** (EEPROM de HAT ? [D, non vérifié]). Sinon : activer l'overlay par défaut (son échec sans carte est à mesurer : [M]) ou le déclencher par une option de la page locale. Valider sur **Pi 4 et Pi 5** [M]. |
| **Actisense NGT-1** (USB)           | `/dev/ttyUSB*` ou équivalent ; connexion Signal K via `canboatjs` [V]                                                                                                                           | Identifiants USB (VID:PID) à relever sur un exemplaire [M] ; règle udev + écriture de la connexion `pipedProviders` dans `settings.json` (Signal K arrêté)                                                                                 |
| **Adaptateurs USB-série NMEA 0183** | `/dev/ttyUSB0` [V](<[doc](https://github.com/SignalK/signalk-server/blob/master/docs/setup/nmea.md)>) ; débit 4800 ou 38400 selon la source [D]                                                 | Détection du débit : [M] ; sinon proposer 4800 par défaut                                                                                                                                                                                  |

La détection se fera par un petit service `fleetai-hwdetect` (udev + script), qui **propose** (statut du plugin, page locale) plutôt qu'il n'impose une connexion. Le périmètre du niveau 1 est la **passerelle NMEA 2000** ; le NMEA 0183 série peut sortir de la première version si la validation matériel traîne.

**Recommandation** : `pi-gen`. **Repli** : CustomPiOS si `pi-gen` s'avère trop lent ou fragile en CI. `rpi-image-gen` à réévaluer plus tard, quand sa compatibilité Imager sera établie. **Reproductibilité** : épingler le commit de `pi-gen`, la version de Signal K et du plugin, et conserver `SBOM`/liste des paquets en artefact ; un build bit-à-bit identique n'est pas garanti (dépôts apt mouvants) [D] — « reproductible » veut ici « refaisable à l'identique en intention, avec rapports ».

### Hébergement et intégrité

- **Releases GitHub** : chaque fichier < 2 GiB, jusqu'à 1000 fichiers par release, **aucune limite de volume total ni de bande passante** [V]([doc GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)). Une image `.img.xz` ≈ 0,7–0,9 Go [D] tient largement ; HaLOS en publie de 780 Mo à 1,6 Go ainsi [V]. Les images tierces de la liste officielle sont hébergées ainsi [V].
- **Intégrité** : `SHA256SUMS` publié avec la release ; signature détachée (minisign ou GPG) du fichier de sommes ; attestation de provenance de GitHub Actions [D, fonctionnalité connue mais non relue ce jour]. L'Imager vérifie `extract_sha256` du manifeste [V], ce qui protège le client **si** le manifeste lui-même est servi en HTTPS depuis un hôte maîtrisé.
- **Dépôt** : à créer **après** la décision de Malo (hors périmètre du spike). Nom proposé dans l'issue : `MaloLebrin/signalk-fleetai-image`.

### Licences (redistribution d'une image)

- Une image Pi OS contient des milliers de paquets Debian à licences mixtes (GPL, LGPL, MIT…) et des composants propres à Raspberry Pi (micrologiciels, chargeur) [D]. Redistribuer est la pratique de tout l'écosystème (HaLOS, OctoPi, MainsailOS [V]) mais impose : fournir les mentions de licences, rendre les sources accessibles pour les paquets GPL (les dépôts Debian et Raspberry Pi suffisent, avec une offre écrite) [D] ; Signal K est Apache-2.0 [V] ; `signalk-fleetai` est MIT [V : brief #1024].
- **Marque** : ne pas nommer l'image « Raspberry Pi OS » ; la politique de marque de Raspberry Pi n'a pas été lue — **à lire avant publication** [D].
- Toute brique GPL ajoutée (Comitup, RaspAP) devient une obligation de redistribution : préférer `wifi-connect` (Apache-2.0) ou du code maison.

## 11. Ce que l'image attend de l'API d'appairage (#1032, partie A)

Contrat déjà décrit dans l'issue (`POST /api/instruments/pairing`, `…/pairing/poll`). L'image et le plugin en tirent ces **exigences**, à porter dans la partie A :

1. **Appel anonyme depuis un appareil sans horloge fiable** : l'API ne doit pas dépendre d'un horodatage client ; `expiresIn` et `interval` sont des durées relatives (déjà le cas dans la RFC 8628).
2. **Champs d'identification facultatifs** envoyés à la création : `deviceLabel` (`fleetai-<4 hex>`), `hardwareKind` (`fleetai-image` au niveau 1 ; `fleetai-kit` au niveau 2), `pluginVersion`, et `imageVersion` (nouveau : utile au support). Un `serialNumber` (Pi) serait un identifiant stable à hacher côté boîtier ; **n'envoyer que l'empreinte**.
3. **Limitation de débit** : une marina ou un partage 4G regroupent plusieurs boîtiers sous une IP ; la limite par IP ne doit pas bloquer des appairages légitimes en parallèle (secondaire par `deviceCode`). Les réponses `429` portent `retryAfter` (comme l'ingestion [V : brief #1024]).
4. **Idempotence du jeton livré une fois** : si le boîtier reçoit le jeton mais plante avant de l'écrire, il est bloqué. Prévoir côté API soit une courte fenêtre de redélivrance au même `deviceCode`, soit un message clair « code consommé » et une action « générer un nouveau jeton » dans l'interface ; côté image, **écriture atomique** du jeton avant tout accusé (comme la file hors-ligne du plugin [V : brief #1024]).
5. **Expiration (10 min) vs boîtier hors-ligne** : sans réseau, aucun code n'existe ; dès le retour d'Internet, le plugin demande un nouveau code. L'API doit tolérer des demandes répétées (aucune limite dure par appareil sur la durée de vie du boîtier, seulement par fenêtre).
6. **Réinitialisation de l'appairage** : l'image fournit une commande/bouton qui efface le jeton et repart en mode appairage ; l'API doit permettre à FleetAi de **révoquer** le jeton d'une source (déjà possible côté jeton d'ingestion) sans contrainte supplémentaire.
7. **TLS** : l'image embarque les certificats racine de Debian ; l'API doit rester joignable en TLS moderne (pas de pinning de certificat côté boîtier).
8. **Point d'accès de l'API configurable** : l'image est livrée avec l'URL de production par défaut, surchargeable pour la préproduction (fichier de configuration sur la partition boot, ou variable du plugin).
9. **Niveau 2 (QR)** : le même `userCode` doit pouvoir être imprimé sur le coffret et saisi via `…/pair?code=ABCD-1234` ; la création d'un appairage **sans attendre l'appel du boîtier** (boîtier préenregistré en usine) reste hors périmètre mais ne doit pas être exclue par le modèle (`claimedByUserId`/`boatId` nuls à la création, conformément à l'issue).
